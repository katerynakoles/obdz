## 2. Ключ шардингу

Обраний ключ: `customer_id`. Обґрунтування (розкладає рівномірно; збирає разом те, що читають разом): `customer_id` має багато різних значень у базі клієнтів, що допомагає рівномірно розподіляти історію замовлень між вузлами, і водночас збирає на одному вузлі всі замовлення та позиції одного клієнта, які зазвичай читають разом в історії покупок

Запит, який подешевшав: отримання всіх замовлень і позицій конкретного клієнта (`WHERE customer_id = ...`). Чому: запит маршрутизується на один конкретний вузол за ключем шардингу і читає лише підмножину записів цього клієнта

Запит, який подорожчав: пошук або агрегація всіх замовлень певного артикулу пряжі (`WHERE sku = 'YR-002'`) чи загальної виручки магазину за день без `customer_id`. Причина (немає ключа шардингу / зʼєднання між вузлами / транзакція на двох вузлах): у запиті немає ключа шардингу, тому координатору доводиться звертатися до всіх вузлів і обʼєднувати часткові результати

Значення ключа, на якому виникне перекіс: `customer_id` постійного оптового покупця або корпоративного акаунта майстерні, який оформлює сотні замовлень щомісяця. Чим це помітно: вузол, куди потрапляє цей `customer_id`, матиме значно більше даних і навантаження на диск/CPU, тоді як інші вузли будуть завантажені слабше

Чому ключ не змінюють на заповненій базі: зміна ключа шардингу вимагає перерозподілу й перезапису всього масиву вже накопичених даних між вузлами з ризиком простоїв і помилок

## 3. Мережевий розділ

Правило області, яке може бути порушене: ...

Сценарій (скільки вузлів, де розірвано мережу, яка операція приходить одночасно на два вузли, що кожен вузол бачить і чого не бачить): ...

| Варіант «відмовити» | Варіант «виконати» |
|---|---|
| збережено: цілісність правила щодо ліміту залишків і відсутність перепродажу товару | збережено: доступність і приймання запитів користувачів на кожному вузлі під час розриву мережі |
| втрачено: доступність виконання цієї операції на вузлі, який не може узгодити стан | втрачено: гарантію дотримання ліміту залишку (можливе перевищення доступної кількості до узгодження) |
| хто це помітить: клієнт або оператор, який отримає відмову при оформленні замовлення | хто це помітить: менеджер складу або клієнт, коли зʼясується нестача мотків після обʼєднання даних |
| мовою CAP обрано: узгодженість відповіді / стану (C) ціною доступності (A) під час розділу (P) | мовою CAP обрано: доступність (A) ціною миттєвої узгодженості (C) під час розділу (P) |

Чому третього варіанта немає, поки мережа розірвана: поки звʼязок між ізольованими частинами мережі розірваний, вузол не може одночасно і гарантувати єдиний узгоджений стан з іншою стороною, і вільно приймати суперечливі зміни без узгодження.

Обраний варіант і ціна помилки, якою вибір обґрунтовано: для списання обмежених складських залишків доцільніше обрати варіант «відмовити» (пріоритет узгодженості над доступністю під час збою мережі), оскільки ціна помилки при перепродажі неіснуючого товару — скасування замовлень, повернення коштів і втрата довіри клієнтів.

Операція, яка витримує остаточну узгодженість: підрахунок кількості переглядів сторінки дашборду або каталогу пряжі. Чому: невелика затримка синхронізації лічильника між вузлами не порушує фінансові чи складські обмеження.

Операція, яка не витримує: списання останнього мотка пряжі конкретної партії під час оформлення замовлення. Чому: затримка узгодження призводить до подвійного списання того самого обмеженого залишку.

Сутність, яку застосунок читає цілком: ...

| Таблиця робочої схеми | Куди потрапила | Чому |

## 7. Повторний запис

Повторний `insertOne`, повний текст помилки:

```text
...
```

Яке обмеження спрацювало: спрацювала обовʼязкова унікальність первинного ключа `_id`, оскільки документ із таким складеним `_id` уже існує в колекції.

| Запуск `updateOne` з `upsert: true` | `matchedCount` | `modifiedCount` | `upsertedCount` | Документів у колекції |
|---|---|---|---|---|
| до запуску | - | - | - | ... |
| перший | ... | ... | ... | ... |
| другий | ... | ... | ... | ... |

Висновок числами: після першого запуску updateOne з upsert: true кількість документів становить [N], а після другого запуску залишається [те саме число N] — повторний запуск не задвоює дані.

Чим ця пара відрізняється від INSERT ... ON CONFLICT роботи №2 і що однакове: однаковим є те, що обидва підходи спираються на унікальний ключ для захисту від дублювання записів і дозволяють зробити запис ідемпотентним; відмінність у тому, що в MongoDB повторний insertOne падає з помилкою E11000 за _id, а updateOne(..., { upsert: true }) оновлює/вставляє документ за фільтром, тоді як у PostgreSQL INSERT ... ON CONFLICT працює на рівні реляційної таблиці з її обмеженнями й транзакціями.

Що сталося б із повторним запуском, якби _id не задавали: MongoDB щоразу згенерувала б новий унікальний ObjectId для _id, тому повторний запуск створив би новий дублікат документа замість виявлення вже наявного запису.

## 8. Агрегація

Файл: [aggregate.js](aggregate.js)

```javascript
db.order_line_events.aggregate([
  {
    $group: {
      _id: "$yarn.sku",
      positions_count: { $sum: 1 },
      total_revenue: { $sum: "$line_total" }
    }
  },
  {
    $sort: { total_revenue: -1 }
  }
])
```

Результат:

```text
{
  _id: 'YR-003',
  positions_count: 2,
  total_revenue: 1560
}
{
  _id: 'YR-002',
  positions_count: 3,
  total_revenue: 1375
}
{
  _id: 'YR-004',
  positions_count: 3,
  total_revenue: 1335
}
{
  _id: 'YR-001',
  positions_count: 2,
  total_revenue: 850
}
```

| Крок конвеєра | Відповідник у SQL |
|---|---|
| `$group` | `GROUP BY` |
| поле `_id` кроку `$group` | вираз/стовпець групування `(yarn.sku)` |
| `$sum` | агрегатна функція `sum()` (або `count(*)` при `$sum: 1`) |
| `$sort` | `ORDER BY` |

Звірка з роботою №3: показник — виручка по артикулах пряжі (YR-003: 1560.00, YR-002: 1350.00, YR-004: 850.00, YR-001: 840.00), число в роботі №3 — 4600.00 сумарно по цих 4 артикулах, число в MongoDB — 4600.00 сумарно (1560 + 1350 + 850 + 840)

Рядків повернула агрегація: 4. Розрізів є насправді: 5 (артикули YR-001..YR-005 у каталозі/вимірі). Якого розрізу немає: артикулу YR-005, по якому не було продажів у перенесених подіях

Чому його немає і що давало повний перелік розрізів у роботах №2 і 3: агрегація йде лише по наявних документах колекції подій без LEFT JOIN до довідника; повний перелік розрізів у роботі №2 давало ліве зʼєднання (LEFT JOIN) з довідниковою таблицею, а в роботі №3 — таблиця виміру (dim_yarns)

Звідки цей перелік можна взяти в документній моделі: з окремої колекції довідника/каталогу (наприклад, yarn_catalog) або з джерела виміру в сховищі/реляційній базі

Імʼя ключа: ... Правило, за яким його складено: ...

| № | Команда | Відповідь |
|---|---|---|
| 1	| SET revenue:2026-09 | 2540.00	OK
| 2	| GET revenue:2026-09	| "2540.00"
| 3 | TTL revenue:2026-09	| (integer) -1
| 4 | EXPIRE revenue:2026-09 25	| (integer) 1
| 5 | TTL revenue:2026-09	| [вставити число, наприклад (integer) 22]
| 6 | EXISTS revenue:2026-09	| (integer) 1
| 7 | GET revenue:2026-09 (після 25 с) | (nil)
| 8 | TTL revenue:2026-09 (integer) | -2
| 9 | SET revenue:2026-09 2540.00 EX 25 | OK
| 10 | INCR dashboard:views:2026-11-28	| (integer) 1

Три відповіді TTL: додатне число — ключ існує і має обмежений час життя в секундах до автоматичного видалення; -1 — ключ існує, але не має заданого строку життя (живе безстроково, поки не видалять/не перезапишуть); -2 — ключ не існує (або вже сплив його час життя).

Час життя в досліді: 25 секунд. Робоче значення для цього показника: 300 секунд (5 хвилин). Обґрунтування (як часто читають, наскільки застаріле значення прийнятне): дашборд продажів може відкриватися кожні кілька хвилин, а затримка оновлення виручки до 5 хвилин є прийнятною для оперативного перегляду показників без зайвого навантаження на сховище; занадто мале TTL збільшує промахи і навантаження на базу, а занадто велике — тримає застарілі цифри.

Чому GET повернув значення в лапках і хто має перетворити його на число: GET повертає рядок (у redis-cli це показано в лапках), бо базова модель «ключ-значення» в Redis зберігає рядкові значення і не знає прикладних числових типів — перетворення на число виконує прикладний код/клієнт.

## 11. Три моделі зберігання

| | Реляційна | Документна | Ключ-значення |
|---|---|---|---|
| форма даних | повʼязані таблиці з рядками та стовпцями певного типу (yarns, orders, order_items)	| документи зі вкладеними обʼєктами (customer, yarn, shipment) у колекціях	| пари «ключ — значення» за ідентифікатором (revenue:2026-09 -> "2540.00") |
| типова операція | транзакційні запити з JOIN, фільтрацією, обмеженнями та агрегаціями	| читання й запис цілого документа картки замовлення або гнучкого каталогу	| миттєве читання (GET) і запис (SET/INCR) готового значення за ключем |
| що обіцяє | транзакції, цілісність правил, ключі та узгоджену схему даних | швидке читання цілісного документа без зʼєднань і гнучку форму полів	| надшвидкий доступ за ключем у памʼяті та простий TTL для кешу |
| чим платимо | складнішим масштабуванням записів і жорсткішою схемою при змінах	| дублюванням полів (ризик аномалій оновлення) і відсутністю перевірки схемою/FK	| відсутністю складних запитів за вмістом значення та тимчасовістю кешу |

| Модель | Доречна задача області | Недоречна задача області |
|---|---|---|
| реляційна | оформлення замовлень, облік поставок, складських залишків і перевірка цілісності звʼязків	| зберігання довільного набору характеристик без єдиної схеми або кешування миттєвих показників під високим читанням |
| документна | зберігання та видача цілісної картки замовлення/позиції або каталогу з різними атрибутами товарів	| суворий контроль міжсутносної посилальної цілісності та багатотабличних транзакційних правил |
| ключ-значення | кешування готових показників дашборду з TTL або лічильників звернень	| складні аналітичні вибірки з фільтрацією та групуванням за довільними полями |

Інші класи нереляційних систем і задача кожного: графові бази даних допомагають шукати звʼязки та шляхи між обʼєктами (наприклад, рекомендації або ланцюжки залежностей), системи сімейства колонок підходять для великих масивів розподілених записів за ключами, а пошукові системи орієнтовані на повнотекстовий пошук за словами

Джерело істини області: реляційна база PostgreSQL. Ознака, за якою це визначено: саме в ній зберігаються первинні записи про замовлення, позиції, залишки та клієнтів із первинними/зовнішніми ключами, обмеженнями та транзакціями, тоді як документи і кеш лише дублюють/прискорюють окремі подання та показники

Чи варто перенести всю область у документну модель: ні, переносити всю область у документну модель не варто. У роботі №1 реляційна схема перевіряла ключі, посилальну цілісність між таблицями (orders, order_items, yarns, customers, shipments) та обмеження коректності даних (NOT NULL, CHECK, унікальність); у документній моделі ці правила вже не перевіряються автоматично схемою бази, а перекладаються на прикладний код, що підвищує ризик неузгодженості складських, фінансових і довідкових даних
